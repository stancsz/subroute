# Independent Critic Report: Control Desk Readiness

**Reviewer:** Independent critic (`/root/control_critic`)
**Date:** 2026-09-24
**Scope:** Original request to make `/control` and the Electron app feel commercially ready; root `AGENTS.md`; `GOAL.md`; `docs/northstar/README.md`; readiness goal; browser control implementation; `desktop/connect.*` and `desktop/main.cjs`.
**Status:** Partial acceptance. Core shared-control and local connection boundaries are present. Commercial-readiness acceptance is not established; visual inspection is incomplete.

## Acceptance findings

- **Shared interface: confirmed in source.** Electron loads `/control?surface=desktop`; browser and Electron therefore share the gateway-hosted HTML, CSS, JS, and routing/usage APIs. Electron-specific folder/agent actions are gated on the preload bridge.
- **Routing policy controls: source contract looks aligned.** Target and advisor have separate provider/model/reasoning controls. UI copy explains alias/force/pass-through policy; helper copy distinguishes client/provider default reasoning and Gemini subscription text-only limits. Runtime `/api/routing-options` returned a structurally compatible payload with OpenAI, Gemini, MiniMax, local, and subscription choices. I did not change routing state.
- **Connection inventory: source contract looks aligned.** `/api/source-status` and `/api/provider-usage` returned current data. Configured/available sources are rendered in the ready list; missing setup and sign-in-required quota are represented separately. Provider quota is not estimated in the client; the usage function uses provider values and leaves unsupported quota as unavailable.
- **Electron recovery and settings boundary: mostly confirmed by inspection.** Failed initial HTTP navigation routes to a bundled connection page. `gateway:connect` accepts only HTTP with localhost/loopback hostnames, rejects URL credentials, probes `/api/source-status` with a timeout before persisting, and stores only the gateway URL. IPC settings calls are constrained to the local connection page. Provider credentials are not part of the settings payload.
- **Commercial readiness: not established by this task or repository thesis.** `docs/northstar/README.md` explicitly says a paid model, supported installer/distribution channel, and commercial support promise are not established. Current changes improve local-product presentation and recovery, but do not supply distribution, update, onboarding, support, or commercial-operability evidence. Do not label this release commercially ready based on UI polish alone.

## Confirmed defects and remaining risks

1. **API failure leaves misleading/incomplete source status.** In `index.html` the connection summary LED is statically green. In `app.js`, `load()` catches errors from both source-status and provider-usage requests but only writes the error into `#updated`; the summary remains “Loading connections…” and the cards remain empty, while the summary LED still looks healthy. If `/control` is served but its APIs are unavailable or fail, this does not satisfy the goal to show actual gateway/provider state. Set an explicit unavailable/error state, remove the green indicator, and give a retry path for inventory as well as quota.
2. **Desktop gateway acceptance is a shallow identity check.** `main.cjs` saves the URL after any successful HTTP response from `/api/source-status`; it does not parse/validate the expected Subroute JSON shape. A different local service mounted at that path could be saved and then load a branded but nonfunctional desk. Validate the response shape (at least a `sources` array with expected fields) before persisting; report a specific incompatibility error.
3. **The connection screen uses absolute trust language.** `connect.html` calls the link “Private connection” and says the address “is checked locally and saved on this device”; the broader route page says “Private by design.” Loopback-only transport is a useful boundary, but the connection is unauthenticated HTTP and this UI establishes neither device-level privacy guarantees nor gateway process identity. Prefer concrete wording such as “Loopback address” and “URL stored in this desktop profile.”
4. **Recovery page does not expose a deliberate retry state after failures beyond resubmitting.** The form is adequate for first-run recovery, but there is no displayed validation of normalized address or a clear field-level error. It is not clear from static inspection whether keyboard/error focus behavior is accessible. Retain input and provide an announced error, focus the invalid field/button as appropriate, and ensure the button is re-enabled after every failure.
5. **Several compact controls and metadata read as prototype density.** The desktop connection page uses 8–11px typography for most copy and controls; the main desk similarly uses 7–11px labels/card metadata. Although the visual tokens are coherent, these sizes risk poor legibility and make connection state, quota reset, and policy consequences feel secondary. Increase body/control text to comfortable desktop sizes and reserve microtype for nonessential identifiers.

The system has a distinct palette and brand mark, but its generic dashboard composition and uniformly compressed metadata still risk feeling like a polished internal console rather than a durable commercial desktop product. ## Follow-up review (2026-09-24)

**Scope:** Re-opened the current source after the initial review, focusing on API failure states, configured-versus-connected wording, privacy wording, and Electron gateway response validation. No implementation changes or tests were run.

### Updated findings

- **Provider inventory failure handling: initial issue is materially fixed.** `load()` now uses `Promise.allSettled`, shows “Provider status unavailable,” marks the connection summary unavailable, removes the green-ready appearance, clears stale provider cards, and leaves a visible refresh retry message. If only quota loading fails while inventory succeeds, configured providers remain visible with an explicit quota-load fallback. The gateway pill changes on fetch transport success/failure. This is substantially more truthful than the first reviewed version.
- **Configured versus connected: mostly improved; one residual phrase still overstates readiness.** The summary now says “sources configured for routing,” and cards use “ENV CONFIGURED”; subscriptions that need sign-in show “ACTION NEEDED,” while unavailable usage is shown separately. These labels distinguish gateway configuration from provider-reported session/quota state. However, the zero-ready empty state still says “No provider connections are ready yet” even though the condition only means no source is both `available` and `configured` in gateway inventory. It does not perform a live provider health check. Rename this to “No provider routes are configured yet” (or equivalent).
- **Privacy wording: connection page corrected; shared browser claim remains conditional.** The Desktop trust panel now says “Loopback address” and that the URL is saved in the Desktop profile; this is concrete and appropriately scoped. The shared `/control` intro still unconditionally says “Loopback gateway / Bound to this device.” Electron enforces loopback, but the browser page can be opened under an origin other than loopback if the service is exposed or proxied. Derive this badge from `location.hostname`, or state the invariant only if the gateway server enforces it at the HTTP boundary. “Provider keys stay in your gateway” is a custody statement, not proof of transport privacy; its current placement on the local connection page is acceptable if gateway-managed secrets remain the only claim.
- **Electron response validation: addressed to a useful minimum.** `gateway:connect` now requires a successful response whose JSON has a non-empty `sources` array and string `id`, `name`, `kind`, and `models` on every row before saving. This rejects generic HTML/JSON health endpoints and supports a clear incompatibility error. Residual hardening: validate the documented booleans such as `available` and `configured` too, so malformed/partial lookalike payloads are rejected consistently. The unauthenticated loopback response still establishes API-shape compatibility, not cryptographic gateway identity; the UI does not claim the latter.

### Visual review and residual size concern

I retried binding the existing Chrome tab, but it is owned by the parent Codex browser session; the isolated reviewer session still cannot capture it. I therefore did not inspect a screenshot at its actual width and cannot claim visual acceptance. Based on current CSS only, body-level control metadata is still very small at normal desktop rendering: card kind 9px, models 9px, connected/usage status 8–10px, labels 9px, route helper copy 10px, usage notice 9px, and the Desktop connection-page helper/link text 9px. Card headings are 12px. At a standard 1240px Electron/browser window, this remains microcopy rather than comfortable product text, especially for provider state and quota reset details. Increase essential status, usage, helper, and form text to at least a readable 12–14px baseline; keep 8–9px only for optional uppercase identifiers. Then inspect the actual browser and Electron screenshots at normal zoom and narrow width before accepting.

The initial source-status failure defect and the broad Electron response-validation gap are substantially resolved in current code. Remaining concrete follow-ups are the misleading zero-ready “connections are ready” phrase, the unconditional browser loopback/device badge, the small essential metadata in CSS, and completing direct visual inspection. Commercial distribution/support readiness remains outside the evidence reviewed here.

This is progress, but small state and quota copy remains hard to scan at normal scale. Actual legibility at the browser screenshot width cannot be certified here.
