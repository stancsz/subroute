# Web search in Codex CLI and Claude Code

Both CLIs can load the project-scoped `subroute-search` MCP server. It calls Subroute's authenticated `POST /v1/alpha/search` for `web_search`; `web_fetch` reads a selected public result page directly over HTTP(S). These are CLI-to-MCP tools, not provider-native web-search tools. The model route remains under Subroute's saved policy.

## Configuration

- `.mcp.json` for Claude Code and `.codex/config.toml` for Codex CLI define `subroute-search`. Claude's project config launches `uv run --no-cache --no-sync --project ${CLAUDE_PROJECT_DIR:-.} --extra search python -m subroute.search_mcp`. Codex's checked-in allowlist exposes `web_search`; that same tool supports explicit single-page reads through `fetch_url`, so no second enabled tool is required. Claude also has a separate `web_fetch(url)` tool.
- Run the Subroute gateway on `127.0.0.1:4000` with its existing SearXNG search tool configured.
- Install `uv` and this project's `search` extra (`uv sync --extra search`). The MCP dependency is pinned in `pyproject.toml`.
- Set `GATEWAY_MASTER_KEY` in the shell that starts Codex CLI or Claude Code. The credential reaches only the local MCP process, which accepts only a loopback HTTP gateway URL and disables proxy inheritance and redirects.
- `SUBROUTE_GATEWAY_URL` is optional and defaults to `http://127.0.0.1:4000`; use another loopback port only for an isolated canary test. Codex forwards it into the MCP process. Claude Code's project config passes only `GATEWAY_MASTER_KEY`, so a canary run needs the gateway URL supplied to the MCP process for that run alone.
- Trust this project in each CLI so it loads project-scoped MCP configuration. Claude Code may ask you to approve the `.mcp.json` server. Restart existing sessions after changing the project config.

## Behavior and limits

Search accepts one to eight queries and bounded `short`, `medium`, or `long` result lengths. It caps output, validates result URLs, and marks search results untrusted. To read one selected result in Codex, call `web_search` again with `fetch_url` set to that exact URL and omit `queries`; do not provide both operations in one call. In Claude Code, call the separate `web_fetch(url)` tool. Fetch only accepts HTTP(S), ports 80/443, no URL credentials, and hostnames resolving exclusively to globally routable IPs. Redirects are rejected (search for the final URL), response bodies are capped at 1 MB, the request deadline is 10 seconds, and only HTML/XHTML/plain text are accepted. HTML script/style/noscript/SVG text is omitted; extracted text is capped at 24,000 characters. Fetched page text is explicitly marked as untrusted data, never instructions. DNS is checked before connection, but without a pinned resolver a DNS-rebinding race is not fully eliminated.

The gateway route accepts only `commands.search_query`, applies the Codex domain allow-list locally, and returns an error rather than an empty result set, so a client cannot read "no evidence" as a verified answer.

LiteLLM 1.103.0 includes provider-gated `websearch_interception` for recognized native search tool definitions. The saved Subroute config enables it only for `openrouter`, using `subroute-searxng`; the canary config enables it for `openrouter` and `minimax`. A MiniMax canary recognized Anthropic's typed `web_search_20250305` definition and executed SearXNG searches, but the request set `max_uses: 1` while the canary logged five search executions across three follow-up patches. The installed interceptor handles `max_agentic_loops` but does not enforce `max_uses`, so the shared config does not enable interception for the `minimax` provider. The project MCP path calls the configured SearXNG search endpoint directly and does not rely on provider tool-schema translation. Anthropic `WebFetch` remains a separate capability, has not been verified through the Codex Subscription or Antigravity routes, and is not widened by this setup.
