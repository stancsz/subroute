# MiniMax M3.1 Flash reliability mitigations (2026-10-23)

## Evidence and defect boundary

The reported drift, stalls, incomplete answers, hallucinations, and loss of focus are user-observed model-quality concerns. This change does not establish their frequency or cause, and does not claim to cure them.

OpenRouter's [current model benchmark page](https://openrouter.ai/minimax/minimax-m3.1-flash) reports 56.2% AA-Omniscience accuracy and 7.2% non-hallucination rate. The latter is not a 92.8% all-answer hallucination rate. [Artificial Analysis explains the benchmark](https://artificialanalysis.ai/articles/aa-omniscience-knowledge-hallucination-benchmark) as incorrect answers divided by incorrect answers plus abstentions, excluding correct answers. Treat these results as task- and setting-dependent, not as a general answer-quality rate.

First-party or project issue reports include [MiniMax M3 malformed array/schema arguments](https://github.com/MiniMax-AI/MiniMax-M3/issues/29), including preview and current reports but not a representative incidence rate; [Hermes reporting Anthropic `thinking.budget_tokens` ignored for M3.1 while documented `output_config.effort` works](https://github.com/NousResearch/hermes-agent/issues/143065); and [long repeated loops reported for older M3](https://github.com/MiniMax-AI/minimax-code/issues/7), which is not evidence about M3.1. These reports are distinct from defects reproduced in this gateway.

Confirmed configuration defects were narrower: all four public Flash aliases selected OpenRouter's `minimax/minimax-m3.1-flash` while forcing `reasoning.exclude: true`, and none advertised supported effort choices. OpenRouter documents that excluding reasoning hides it from the response but does not prevent reasoning-token cost or exhaustion of `max_tokens`; visible output can therefore be empty. This gateway setting was counterproductive for transparency and did not constrain reasoning cost.

MiniMax's [Text Generation guide](https://platform.minimax.io/docs/guides/text-generation) documents `max` as the default effort and supports `low`, `medium`, `high`, `xhigh`, and `max`. The route now defaults to `medium` only when the caller has not supplied an effort or reasoning-token budget. The deployment hook maps Flash caller/desk effort to OpenRouter's native `reasoning.effort`, not `reasoning_effort`: local LiteLLM 1.101.0's old OpenRouter cost metadata rejects the latter before provider dispatch. Production and staging run LiteLLM 1.103.0. Native mapping also preserves MiniMax's distinct `max` value rather than letting LiteLLM remap `max` to `xhigh`. The actual deployment model is the identity boundary; routing metadata alone is not used, so a fallback attempt on another provider does not inherit Flash settings. The direct `minimax` alias remains `minimax/MiniMax-M3`; it is not the Flash route and was not changed.

MiniMax's [M3 function-calling guide](https://platform.minimax.io/docs/guides/text-m3-function-call) requires replaying the complete assistant response, including `reasoning_content`. The hook changes only effort carriers; it does not rewrite message history, tool calls, output limits, or timeouts. This is a code-boundary assertion, not an upstream provider round-trip test.

## Implementation choice

LiteLLM remains the owner of Chat, Responses, and Messages translation. The installed Router source (`.venv/Lib/site-packages/litellm/router.py`, `_drop_client_effort_carriers_a_tier_pin_supersedes`) documents that a deployment-level `reasoning_effort` pin removes caller effort carriers such as `thinking`, `output_config.effort`, and `reasoning.effort`. That native config would violate caller override precedence, so the gateway applies the default in its deployment hook instead. Existing routing-desk overrides remain higher priority; explicit caller controls remain higher priority than the default.

The Advisor brief now anchors recommendations to the current objective and latest correction, distinguishes verified tool results from assistant claims, flags repeated failed approaches, calls for one changed action, and requires evidence before recommending completion. Selection rules, invocation budgets, and call count are unchanged. Broader drift/repetition detection would need a separate design and is not implemented here.

It also covers fallback model identity, precedence, history immutability, and unaffected routes. This fixture is not a live provider test.

This did not demonstrate quality improvement; the loop case returned reasoning in the medium arm while baseline hid it. ## Native Claude Code profile

The actual Claude Code 2.1.251 requests sent through gateway port 4000 selected model group `minimax-flash`; observed attempted retries/fallbacks were zero. The disposable acceptance task was the paired stdlib appointment task in `tests/acceptance/qwen_claude/appointment_slots`, with an external 10-test holdout. Only two source files were changed. This evidence supports a scoped profile, not a claim that either prompt or effort is universally optimal.

With the full system prompt (~15,120 characters), low effort passed the first run (133.290 s, 4 visible checks plus 10 holdouts), but a second run (96.622 s) reached native `error_max_turns` without final handoff and failed the holdout despite passing visible checks. Full-prompt medium passed visible checks in 67.991 s but missed one strict `HH:MM` holdout; a repeat (107.894 s) passed all 14 checks. Lean prompt (~5,268 characters) with medium passed all 14 in 93.648 s. Medium is therefore a provisional safer completion balance for this profile. These small trials do not establish a universal optimum or causal cure.

The harness used a nominal 24-turn and 240-second outer deadline. Native `num_turns` accounting may differ: the first low run reported 29 versus 24 observed requests. Some extra tool commands were denied by the narrow fixture allowlist, a harness confound. OpenRouter usage is billable; these results are not an invoice or a claim that testing was free. Parent checks recorded 29 feature and 4 additional correct-responses wire-acceptance passes; the 256-case matrix passed, alongside 6 baseline failures (2 Gemini and 4 reasoning-policy) already recorded as debt. Production was reloaded at 19:56Z and ready at 19:57Z; staging was reloaded at 19:54Z. Provider-only and real production-CLI evidence are separate. The account MiniMax-plus-Cloudflare guardrail remains unchanged. Normal tool calls worked, but forced named-tool choice returned 404 `provider-not-allowed-by-guardrail` and remains unsupported under current policy.

These are tiny trials with a narrow task, small sample, fixture allowlist denials, and native turn-count differences. They are confounded evidence for this setup, not a hallucination cure, a causal quality improvement, or an optimum effort/prompt claim.

The opt-in launcher `scripts/claude-minimax.ps1` uses the installed native Claude executable, clears inherited `ANTHROPIC_*` and conflicting simple/effort environment values only for the child invocation, and restores them in `finally`. It supplies an empty `--setting-sources=` plus a dedicated user-local profile, without bypass-permission or bare-mode flags. On first use, the launcher creates `~/.claude/subroute-minimax.settings.json` only if it does not already exist and requires `GATEWAY_MASTER_KEY` in the current process for that creation. It never overwrites an existing profile. The key is stored only in that local profile; global settings are not changed. For example, run `./scripts/claude-minimax.ps1 --effort low` to override the profile's `medium` default for one invocation; omit `--effort` to use `medium`.

In profile acceptance run 1, the repaired coding task passed all 14 checks but then hit native `error_max_turns` at 12 turns without a final handoff; five diagnostics were denied, and elapsed time was 57.29 seconds. The final profile-r2 read-only receipt records a successful completed run with all 14 checks passing (4 visible and 10 holdout), exit code 0, and 102.95 seconds. The receipt records a permission denial, so this is not evidence that every diagnostic was allowed. These small, task-specific runs do not establish a universal optimum or causal cure.

## Direct MiniMax M3.1 Flash selectable route

`minimax-flash-direct` is a separate selectable alias for `minimax/MiniMax-M3.1-Flash`, using `MINIMAX_API_KEY`. It preserves the OpenRouter alias and fallback configuration. The direct alias deliberately omits `api_base`: LiteLLM's MiniMax adapter selects protocol-specific defaults, while the Chat-only `https://api.minimax.io/v1` pin incorrectly sent native Messages to `/v1/v1/messages`. When no caller effort or thinking budget is present, the existing routing hook supplies medium; caller effort is honored, and saved routing-desk effort takes precedence. Direct Chat/Responses use LiteLLM's MiniMax-native `reasoning_effort` carrier, while Messages uses its native `output_config.effort` translation. The direct model is matched by its exact provider model string, so fallback attempts on other providers do not inherit this default.

LiteLLM 1.106.2 lacks capability metadata for this model, so its native Anthropic configuration treated it as an older Claude model and silently removed `output_config.effort` and adaptive-thinking controls. The direct alias now declares `supports_reasoning`, `supports_adaptive_thinking`, and `supports_output_config` in the existing YAML model metadata. The configured Router registers these flags on the exact provider model, allowing LiteLLM's native Messages handling to retain the controls. A targeted `allowed_openai_params: [reasoning_effort]` remains necessary: the installed MiniMax Chat adapter rejects this documented field otherwise, including on LiteLLM's native Responses-to-Chat bridge. Remove the allowlist once the native MiniMax Chat adapter supports that documented parameter; remove the explicit capability flags once native model metadata preserves the same behavior. The alias still omits `api_base`, preserving protocol-specific defaults. Responses calls therefore emit Chat `reasoning_effort`, while Messages uses native `output_config.effort`. The configured-Router fixture in `tests/test_minimax_direct_provider.py` checks terminal success, usage, effort, and output limits without provider credentials.

Parent acceptance passed 43 checks on LiteLLM 1.106.2, including nine independently authored default/override cases across Chat, Responses and Messages. Ten historical proxy fixtures were deselected because concurrent Advisor changes require a field absent from that local unpatched dependency; this is not full-suite acceptance. The final output is `.runs/minimax-reliability/direct-flash-acceptance-final.txt`. A separate native MiniMax Chat probe made two real provider calls in 2.75 seconds: validated automatic tool arguments, complete assistant/tool replay, exact `DIRECT_FLASH_OK`, terminal `stop`, provider usage and native status zero. Its receipt is `.runs/minimax-reliability/direct-flash-live-native.json`. This verifies that narrow native Chat interaction, not live gateway alias availability, all-protocol provider compatibility or improved model quality. Full assistant-history replay remains the client's responsibility.
