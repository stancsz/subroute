## Readiness and provider health

LiteLLM 1.103.0's `/health` runs provider checks; `/health/readiness` checks whether the gateway and database are ready to serve. Before the final adjustment, `/health` launched checks for all deployments without a concurrency bound. Two gateway instances could therefore exceed the Antigravity sidecar's four-process capacity and make health probes themselves fail with 429.

The Compose gateways set LiteLLM's supported `health_check_concurrency: 2`; `HEALTH_CHECK_TIMEOUT_SECONDS=10` bounds each provider probe. LiteLLM's native `disable_background_health_check` plus `health_check_skip_disabled_background_models` exclude virtual `current` from provider checks while leaving dynamic routing intact. With 17 public IDs, 16 deployments are health-probed, for an 80-second upper bound (`ceil(16 / 2) × 10s`). After the final Compose recreation, independent full health calls returned HTTP 200 in 21.34 seconds on production and 19.31 seconds on staging, each with 14 healthy and 2 unhealthy. The only unhealthy paths are FreeToken and Ollama, excluded by the user. OpenRouter, all four Gemini Subscription routes, all five Codex target/Reserve routes, and all three Codex Advisor routes were healthy on both. A prior overlapping two-gateway health + provider-usage refresh showed production Gemini 3.8 unhealthy once; its immediate isolated health rerun recovered, and no matching sidecar 429 was found, so the cause remains unknown. Readiness on both returned HTTP 200 with PostgreSQL connected.

After the final Compose recreation, 50 readiness requests per gateway all returned HTTP 200; p95/max were 39.9/63.7 ms on production and 30.0/34.3 ms on staging. Independent full `/health` calls returned 14 healthy and only the two user-excluded local endpoints unhealthy on both gateways. Antigravity logs showed no 429 during the provider-health checks.

The deliberately small OpenRouter `max_tokens=20` probes returned HTTP 200 with `finish_reason=length` and `content=null`; provider usage showed all 20 completion tokens consumed, including reasoning. A separate genuine post-restart OpenRouter call at `max_tokens=128` similarly exhausted the cap, returning 128 completion tokens, `content=null`, and $0.00016842 cost. The public request explicitly targeted the provider by temporarily setting staging routing mode to `off`; this was necessary because the saved `force` mode correctly sends every request to its selected active model. No gateway code increased or removed the caller cap. An explicit 256-token probe completed successfully. Captured earlier costs were $0.00011616 and $0.00008878; final public buffered/SSE costs were $0.00010341 and $0.00011155, and a successful force-route call cost $0.00014465. Two adapter-level diagnostic calls outside the public gateway reported $0.00011497 and $0.00011543. These are captured calls, not a complete provider spend total for the overall test session.

Before those generations, the live usage endpoint reported OpenAI Subscription ready at 32% used, OpenRouter ready at $5.105187 / $10 used, and Gemini Subscription connected with 14 models. These quota/status reads are distinct from the completion receipts.

## 2026-09-29 advisor failure classification follow-up

The selected pre-call advisor remains fail-closed: an advisor failure prevents the base model dispatch. A previous generic `RuntimeError` made bridge oversize failures surface as HTTP 500. The plugin now raises a bounded LiteLLM hook `HTTPException` with a status chosen from the typed error: invalid translated input 400, bridge request over 1 MB 413, bridge/provider quota 429, timeout 504, and upstream authentication/connectivity/server failures 502. The response includes request and consultation IDs but not provider raw error text; the correlated log stores the sanitized, capped reason. Direct OpenAI GPT-5.2 Codex API and Gemini API modes remain excluded.

This uses LiteLLM 1.103.0's existing hook exception path rather than adding a custom route. A real staging `/v1/messages` request exceeding the bridge size boundary returned HTTP 413 with Anthropic's `type: error` envelope and both IDs; size validation happened before contacting the sidecar, and the base provider was not dispatched. A valid Gemini target request immediately afterward succeeded. Before the final Gemini target-timeout status change, a complete live matrix passed 9 tests in 67.26 seconds across all enabled Gemini Subscription, Codex Subscription/Advisor, and OpenRouter routes. The Codex status mapping tests simulate upstream 401/408/429/500/503 responses through HTTPX MockTransport, mapping credential/service errors to 502, quota to 429, and timeouts to 504 without retries. This is adapter evidence, not live injection of actual external auth/quota/outage faults.

## Limits and next action

The live subscription matrix exercises configured Gemini and Codex aliases plus OpenRouter; it does not prove external provider auth/quota/service-down/timeout handling. Direct Gemini API and GPT-5.2 Codex API are intentionally out of scope and were not used. The administrative `/key/info` request without a token was reconfirmed as a LiteLLM 1.103.0 500 (`where.token` missing); the Agent Skills index is deliberately gated by LiteLLM's `public_skills_index` flag and returns 404 while that feature remains disabled. Neither is part of the requested provider routing path. These are scoped observations, not blockers to the completed gateway reliability objective. The 8-pass/1-fail matrix result above is a historical run; the final-source matrix later passed 10/10 and the 2026-09-29 closeout rerun also passed 10/10 in 68.88 seconds. The complete locked suite passed 250 tests with 10 explicit live-only skips. See the closeout record in [GOAL.md](../../GOAL.md).
