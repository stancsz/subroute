# Advisor request and attempt correlation

## Scope

This is a post-closure improvement to the scoped simplicity delivery. It does not change normal routing, provider request bodies, Sift selection, or the completed ten-criterion acceptance record. It carries the gateway request ID and one advisor-attempt ID across the private Experts HTTP hop so the existing accounting and Sift records can be joined reliably.

## Failure mechanism and ownership

Before this change, accounting already created request and per-attempt records, but the IDs did not cross the private 4040 adapter boundary. Concurrent consultations could therefore lack a reliable join key between gateway accounting and the Sift audit. The gateway now injects the pair only for the `advisor` role at the exact configured `http://experts:4040` base. LiteLLM carries them as HTTP headers, outside the JSON body.

At the Experts callback, the pair is accepted only when LiteLLM supplies a `UserAPIKeyAuth` with `PROXY_ADMIN` and `LITELLM_PROXY_MASTER_KEY_ALIAS`. Presented IDs are always stripped from the recognized request and provider-header carriers; an untrusted marker or UUID-formatted caller value cannot claim a Sift log association. The pair is validated as UUIDs, copied into request-local audit state, and removed on success, failure, cancellation, and multimodal bypass. This changes audit correlation only; UUIDs are not authentication credentials.

Relevant source: `src/subroute/usage_accounting.py` (root request and advisor attempt), `src/subroute/plugins/expert_sift.py` (auth gate, header consumption, marker cleanup), and `src/sift/litellm_proxy.py` (correlated audit log fields).

### Master-key HTTP auth regression check

`test_litellm_master_key_http_auth_enables_expert_correlation` sends a local FastAPI `TestClient` request through LiteLLM's actual `user_api_key_auth` dependency, parses the posted request body, then calls the installed `ProxyLogging.pre_call_hook` with `ExpertSiftHook` registered in `litellm.callbacks`. The real hook validates the authenticated identity, compacts the text using a local counting-router fixture, logs the matching request/attempt IDs, and removes its marker and reserved headers. The test requires `compacted=true`, more input than forwarded tokens, the configured target, and exact request/attempt ID matches. Independent read-only review confirmed the posted body is used and found no remaining issue within this test's scope. The route itself is test-owned, and the token counter is synthetic; the test does not invoke LiteLLM's actual `/v1/messages` endpoint or a provider transport. It strengthens local auth-to-callback-to-Sift evidence without closing provider or staging acceptance.

`test_real_litellm_messages_route_correlates_expert_call_and_strips_headers` extends that coverage through LiteLLM's actual FastAPI `/v1/messages` route and project-locked 1.106.2 `Router`. It uses real master-key auth, posts correlation IDs with the request, triggers Expert Sift through registered callbacks, and verifies the Sift audit, compacted response header, and request headers passed to the completion adapter stub. The fixture replaces `litellm.acompletion`, so it proves the headers have been stripped by the adapter-call boundary but does not observe serialized provider HTTP headers or provider acceptance. Independent review of the pinned source found no mismatch in the callback discovery path; it confirmed this boundary explicitly.

## Runtime limits

At the source-validation checkpoint, staging and Experts still used the earlier immutable image. The candidate was later deployed only to `gateway-staging` and `experts`; the production gateway stayed on its previous image. Current hashes, service state, policy, and the one bounded request are recorded in the [staging smoke receipt](receipts/advisor-correlation-staging-smoke-2026-10-25.json).

The staging smoke posted one small Anthropic Messages request to the actual host-mapped staging port `4005`, with the existing policy unchanged and request-level fallback disabled. A first connection attempt to container-local port `4000` was refused before HTTP; after verifying the actual binding, the same request ID was used on port `4005`, so only one request reached the gateway. The exact request ID produced three complete, usage-complete ledger rows in order: MiniMax target, an Experts HTTP hop using the Gemini Advisor route, then MiniMax target. No fallback row appeared. This proves one forced Advisor-tool round trip through the candidate image and an exact request-level ledger cohort. It does not prove natural optional-tool selection.

The Experts config names `subroute.plugins.expert_sift.expert_sift_hook`, and the in-container `expert_sift.py` hash matches the reviewed worktree. However, the request's Advisor input was only 1,047 provider-reported tokens, below the 25,600-token compaction target. No matching `sift_request` line appeared in the observed Experts container logs, and the outer target response contained no Sift headers. Therefore live Sift execution, correlation pair arrival at the audit, and large-input compaction remain **unverified**. The request used an explicit Advisor tool choice, so it does not establish that a naturally optional tool is selected on ordinary prompts. No repeated provider request, staging policy change, or production change was made.

The implementation remains based on project-pinned LiteLLM 1.106.2. The local route test proves callback discovery, auth, Sift audit behavior under a fixture, and header removal at the adapter stub. The staging smoke adds real provider and 4040 round-trip evidence, but not captured upstream HTTP headers or a visible Sift audit record. The exact-base check also assumes the deployed private Expert URL remains `http://experts:4040`.
