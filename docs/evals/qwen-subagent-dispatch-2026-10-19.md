## Interpretation and next use

1. `--bare` disables the child-agent path for this use, even with an explicit `--agents` argument. Do not use it when a Qwen session must spawn nested Claude Code agents.
2. Sift is request middleware and context compaction, not the agent scheduler. Claude Code supplied `Agent`; Subroute selected Qwen; Sift audited each request. A small coding task may never trigger compaction.
3. Qwen is not a dependable orchestrator in this setup. For actual product changes, Codex should own orchestration and launch one bounded Qwen worker through the existing native CLI harness, then independently inspect and verify its artifact. Do not rely on Qwen to recursively coordinate workers or treat its terminal text as acceptance.
4. Historical coding evidence is mixed: the Oct 14 route-rules and JSONL-report fixtures passed source tests, but only one of two shell-enabled test loops completed; the Oct 15 domain pilot had later independent holdout failures. See `docs/evals/qwen-claude-acceptance-2026-10-14.md` and `docs/evals/qwen-claude-domains-and-sift-2026-10-15.md`.

## Broad-request controller prototype — 2026-10-20

To address the repeated timeout and orchestration weaknesses, added an experimental plan/execute/verify runner in `tests/acceptance/qwen_claude/autonomous.py`. It asks Qwen to plan against explicit requirement IDs, checks that every requirement maps to a step and final validator, gives each worker its assigned acceptance text, serializes implementation steps, and treats runner validators rather than model claims as acceptance. It records step and retry checkpoints, allows one continuation for a failed or no-op worker and one final integration repair, hashes generated/cache paths for scope accounting, and can classify an interrupted run while blocking automatic resume. An explicit disposable-workspace manifest is required.

Focused validation: 12 autonomous-runner tests and 4 existing child-repair tests pass; Python compilation and `git diff --check` pass. Independent read-only QA initially rejected the prototype, then found the principal interim/final validation, requirement mapping, retry checkpointing, and path-hash gaps repaired. The reviewer considers one guarded trial reasonable only in a fresh disposable copy/worktree, with human-reviewed requirement-to-validator mappings and independent post-run acceptance. Remaining limitation: the manifest is an attestation rather than OS-enforced filesystem isolation; out-of-scope writes are detected after the fact. A single trial would not establish unattended reliability. No live Qwen broad-task run has been made with this prototype yet.

The Advisor Council recommended a persistent plan/execute/verify controller: Qwen may own the dependency-aware plan and bounded implementation/repair, while the runner owns timeouts, checkpoints, scope, tests, and truthful completion. Gemini also advised against a rigid two-file cap. Treat the controller as an experiment; retain the known operating conclusion that Qwen is useful as a supervised implementation leaf and repair worker, not yet a reliable owner of broad product delivery.

## Plan: make local Qwen dependable for end-to-end work — 2026-10-20

### Current evidence and goal

Use Qwen 3.8 27B as a bounded implementation worker behind Claude Code/Sift. Codex remains accountable for task framing, integration and acceptance. “End-to-end worthy” means a real user workflow passes its declared acceptance checks, failures are surfaced instead of narrated away, and a separate reviewer can reproduce the result. It does not mean Qwen can safely own an open-ended product request by itself.

Evidence already in this evaluation: Qwen completed scoped single-file and multi-file implementations, and one visible-test repair; it has also confidently missed an ambiguous-time requirement, returned before a spawned child finished, and sometimes spent most of its time on unrelated exploration. The broad-request controller adds explicit requirements, bounded steps, path/hash tracking, runner-owned validators and one repair path. This run was interrupted by an explicit stop while a worker step was in progress; its hashes show no files changed. The controller intentionally does not resume a live worker attempt. Keep the run as interrupted evidence and start again from a clean disposable copy.

### Operating plan

1. **Frame one user workflow.** State the user-visible outcome, requirement IDs, observable acceptance tests, exact source write scopes, read-only criteria/spec, protected data and external-effect limits. Reject a plan if any requirement has no implementation step or validator. Do not ask Qwen to build the whole Jane/Vagaro clone in one run.
2. **Keep orchestration deterministic.** Qwen may propose an ordered plan; the controller validates coverage, dependencies, path safety and step size. Execute one named foreground child per step, without recursive delegation. Give the child only the files and acceptance details needed for that step. Keep shell/test execution and hidden holdouts with the runner/reviewer.
3. **Gate every handoff with evidence.** Hash the disposable workspace before and after each attempt; reject out-of-scope edits and test/spec changes. Run declared checks after the worker returns. If a bounded attempt has a visible failure, send only actionable visible diagnostics to one repair attempt, then rerun all affected checks. Hidden holdouts and final user-workflow checks remain independent acceptance evidence.
4. **Treat interruption as a transaction boundary.** Never continue a workspace while its write step might still be alive. Reconcile the saved hashes, preserve transcript and partial workspace, and restart from a clean copy unless the runner later gains an explicit tested checkpoint/rollback mechanism. Record interrupted work as interrupted, not as a Qwen quality failure or a pass.
5. **Accept the product slice independently.** A nonauthor reviewer uses an isolated environment to exercise the actual owner/practitioner/anonymous workflow and relevant persistence, authorization and failure cases. Re-run only checks affected by repairs. The worker's final message, a passing unit suite, or a healthy HTTP response alone cannot close the task.
6. **Grow capability by matched trials.** First finish the current reminder-outbox workflow. Then run three small representative tasks—one ordinary UI/API feature, one data-lifecycle change, and one repair from a seeded failing acceptance test—using the same runner and independent acceptance. Compare request-to-verified-delivery, repair count, scope violations, false-success events and elapsed time from saved transcripts. Keep Qwen for bounded work if these pass; narrow its role or improve the controller only when evidence identifies a repeatable failure cause. Do not infer general reliability from a single success.
7. **Keep operations observable and cheap.** Each run should retain a concise plan, validator output, worker/repair transcripts, changed-path hashes, route/Sift call counts, duration and final independent verdict. Start the local model only for a scheduled task batch and verify the Compose service is stopped afterward when no Qwen work remains. Do not claim Sift compacted context unless the audit confirms a request crossed its configured threshold.

### Current execution and acceptance gate

Restart the approved local `appointment reminder preparation outbox` trial from an unchanged copy of the disposable app workspace. Keep the model on `qwen3.8-27b`, the staging gateway on its existing configuration, and the scratch workspace isolated. Allow the controller's existing bounded plan/execute/visible-repair flow.
