# Durable usage receipts

Status: serving accounting release accepted on 2026-10-11. The [acceptance record](../goal/usage-accounting.md) identifies tested source, repository gates, real calls and receipt transfer in both public environments. Remaining measurement, transfer and dependency bounds are described below.

## What is recorded

The configured `subroute.usage_accounting.usage_accounting` callback writes a pending receipt before each LiteLLM deployment attempt. Direct Codex advisor and Luna compaction calls use the same receipt store; Router compaction has the compaction role. A failed initial database write denies inference with 503. There is no additional runtime service or database: production and staging use their existing, separate PostgreSQL stores through the proxy's generated Prisma connection.

The receipt contains request/attempt IDs, server identity, environment, path, model/provider labels, role, outcome, revisions, timestamps and recognized numeric usage. It contains no API credential, request/response body, tool arguments, caller metadata or provider error body. Provider cost is recorded only when reported explicitly. LiteLLM price-table costs and token-count estimates are excluded. Missing counts/cost remain absent, and explicitly reported zero remains zero. Native Anthropic input counts and cache-read/cache-creation fields remain separate measurements.

Completed direct Advisor calls with provider-reported input and output tokens are also mirrored into LiteLLM's `LiteLLM_SpendLogs` so the Admin UI Logs page shows a separate `advisor` row. The row uses a distinct `subroute-advisor-<attempt-id>` request ID, the Advisor model and provider, and the observed tokens. It never stores the prompt or advice. When the provider does not report cost, the required SpendLogs `spend` field is zero and `metadata.provider_cost_reported` is false; zero there means unreported cost, not proof of free usage. The durable receipt remains the source of truth. Mirror failures are logged and can be repaired by an idempotent backfill from completed receipts.

Each actual provider call has `kind=provider`. Protocol translation layers have `kind=bridge`; never add their tokens to underlying provider totals. Cache hits are `outcome=cached` with no new provider consumption. A pending row proves planned dispatch, not that a provider received a request. Completion requires a terminal outcome with measured input and output counts for `usage_complete=true`. Incomplete/failed/cancelled/interrupted rows retain available partial facts without claiming completion.

## Attribution and transfer

Set `SUBROUTE_ENVIRONMENT` to `production` or `staging` in the corresponding gateway. Cloudflare customer identity requires `x-subroute-accounting-grant`, a UTF-8 JSON payload signed with HMAC-SHA256 using the separate `SUBROUTE_ACCOUNTING_SECRET`. The grant binds environment, request/parent attempt, customer/key ID, exact inference path, role and a maximum 120-second expiry. The bridge forwards it only after authenticating the existing inference service token. Caller metadata cannot override identity or authorize advisor accounting. Framework-owned internal advisor orchestration inherits the parent and records its advisor calls separately.

Direct local calls have no Cloudflare customer. An authoritative LiteLLM virtual-key authentication object permits a SHA-256 identity for that local credential; keyless loopback remains `local-unattributed`. A presented Authorization header alone does not establish identity on a keyless gateway.

The existing public staging Worker uses the production inference router. Its signed staging receipts therefore live in that router's PostgreSQL store with staging attribution; direct staging loopback traffic uses the separate staging database. Each Cloudflare environment polls both configured stores for its own environment. Selecting a telemetry store does not change inference routing or let a caller select a database.

Known direct inference aliases normalize to their `/v1/` paths for receipt transfer, including chat, Responses, Messages, images, completions, embeddings, audio, moderation and rerank. Other direct SDK/background calls use `/local`. Signed grants are verified against the exact incoming path first; normalization never broadens the public inference bridge's route allowlist.

The database table `subroute_usage_receipts` and its pending-outbox index are created lazily on first use. The runtime database role needs permission to create this additive table/index. SQL calls have three-second deadlines. Numeric checkpoints are written at most once every 15 seconds after the first write, up to 41 checkpoints, plus finalization. A failed write does not suppress a later retry of unchanged facts. On reading the outbox, at most 100 pending rows older than 15 minutes become interrupted; their measurements are preserved. Late facts can enrich interrupted rows without reviving their outcomes.

Only these telemetry routes are exposed through the protected bridge:

- `GET /internal/accounting/receipts?environment=production|staging`: at most 100 unacknowledged receipt revisions.
- `POST /internal/accounting/ack?environment=production|staging`: an object with `receipts: [{attempt_id, revision}]`, at most 100 items and 16 KiB.

Both require `x-subroute-accounting-token` equal to the separate accounting secret, at least 32 characters. The inference bridge token and caller keys cannot read or acknowledge telemetry. The bridge's `store=production|staging` selects a configured loopback database endpoint; it is not an arbitrary target URL or management proxy.

Cloudflare writes allowlisted receipt fields to its environment's D1 `provider_attempt_usage` table and verifies the persisted revision before acknowledging. It requires an exact matching bridge parent for Cloudflare customers. Replayed/stale revisions do not overwrite newer facts or double-charge wallets. A lost acknowledgement leaves the outbox available for idempotent retry; an acknowledgement of revision 2 cannot hide revision 3. Both Workers poll both router stores for their own environment because the public staging Worker currently uses the production inference router, while direct local staging uses the staging router database.

## Rollout and recovery

1. Complete repository checks and independent acceptance before promotion. Preserve any unrelated configuration edits. Production uses digest-pinned LiteLLM 1.103.0; the development lock remains 1.101.0 because the optional music extra pins MCP 1.28.1, which conflicts with 1.103.0's proxy dependency on MCP 2.2 or newer. A resolution attempt confirmed this conflict. Do not upgrade that separate integration as an accounting change. Test the accounting hooks against both pinned versions, and use a fresh process in the serving image with an isolated PostgreSQL fixture to verify its generated Prisma/runtime behavior. The development suite alone does not establish deployed-version parity. Retire this split only with a separately verified music/MCP migration.
2. Generate one separate random accounting service secret in ignored local storage. Configure it in both Subroute gateway environments and as `SUBROUTE_ACCOUNTING_SECRET` in both Cloudflare Workers. Configure the bridge secret file `local/secrets/accounting_token` in the sibling gateway repository. Do not print or commit its contents. Keep it distinct from the inference bridge token.
3. Apply the sibling gateway's additive D1 migrations 0007 and 0008 to both databases before publishing the updated Workers. Configure `LOCAL_ACCOUNTING_STAGING_TARGET` to the existing staging loopback endpoint. Roll out/restart the gateways and rebuild the bridge only under the owner's deployment authorization. Restarting a gateway can interrupt active requests; retain their pending receipts.
4. Read back readiness, serving source/version, separate databases, telemetry authorization and one complete receipt transfer per environment. The existing Worker cron runs every 15 minutes; metadata is eventually visible in D1, not immediately guaranteed. Backlogs and outages can extend that delay. Full live inference/harness acceptance and durable evidence are required before declaring completion.
5. For transfer outages, keep the PostgreSQL outbox and repair the connection/configuration. Re-run collection after recovery; do not replay inference or manually acknowledge unsaved revisions. A rejected parent/environment/identity is an integrity error requiring investigation, not a reason to relax validation.

The accounting secret authenticates both receipt reads and short-lived grants. Rotate the shared configuration together; in-flight old grants may then fail closed. Existing receipts contain no bearer secret and remain transferable under the new service secret. Losing or deleting the PostgreSQL store before an unacknowledged revision transfers loses those facts. There is no automatic retention purge or archive job. Keep outbox/identity/idempotency data until a separately tested retention policy is released.

## Framework workaround and remaining limits

For observed streams, the parser/close observer owns settlement. LiteLLM 1.101.0/1.103.0's native Responses `_run_post_success_hooks` blocks the serving loop while running its async deployment success hook in a separate worker loop. Reusing Prisma's async HTTP pool there raises `RuntimeError` because its connection belongs to the serving loop. The deployment success and aggregate success callbacks therefore skip duplicate writes for observed streams; buffered and cache accounting retain their existing paths. This uses the existing observers and adds no database client, task queue, or retry. Keep this ownership rule while these observers are installed, and reevaluate it when replacing them with upstream accounting hooks. Receipt write errors include only the attempt ID and exception type, without exception bodies or SQL parameters. See the [2026-10-15 staging evidence](../evals/counting-and-receipts-2026-10-15.md).

LiteLLM 1.101.0 and 1.103.0 assemble missing stream usage using estimates and can inject estimated cost into native Responses usage. Their deployment hook also misses raw native Messages usage and cancellation between chunks. Version-bounded observers retain numeric provider facts before these transformations, leave output bytes/schema unchanged, and close/finalize native Responses streams on cancellation. They reuse the framework's parsed native Responses objects and SSE decoder. Retire these observers only when an upstream version exposes actual provider-origin usage and cancellation for the same installed-framework regressions. An unreviewed LiteLLM version fails startup rather than silently using incompatible hooks.

No verified read-only per-generation recovery exists here for MiMo coding-plan or Codex subscription calls. An abrupt process loss can leave only the last successful checkpoint. The native Messages observer bounds an individual telemetry SSE frame at 64 KiB; an oversized frame can therefore leave its usage unknown while normal framework transport remains unchanged. The native Responses observer reuses the framework's parsed snapshot without this additional event-size limit. A timeout or customer disconnect does not prove the provider stopped billing. Provider consumption, delivered request outcome and customer wallet charge are separate facts.

Offline checks include installed Router/custom-provider calls, native/translated loopback HTTP fixtures and a disposable PostgreSQL fixture. These do not establish live provider compatibility. Use the goal's dated release evidence for the accepted source and real-call results.

Chat stream settlement belongs to the actual provider parser, not LiteLLM's delegating fallback wrapper. An explicit provider finish is completion proof; clean EOF without that proof is interrupted, and a real disconnect before it is cancelled. Provider completion and client delivery can differ. The accounting observer reads the provider value before LiteLLM strips its finish reason and requires this proof even when the framework emits a synthetic final chunk. ASGI fixtures exercise the real Router, proxy serializer and final cleanup because plain iteration does not cover the outer-wrapper lifecycle.
