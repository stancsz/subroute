## Source-grounded continuation

The active goal continued after the two rejected trials. A read-only investigation found a concrete execution boundary in the exact pinned build: [`ggml-cuda.cu`](https://github.com/ggml-org/llama.cpp/blob/091b6a7fc561b78da90a0ed2d524ec995458c657/ggml/src/ggml-cuda/ggml-cuda.cu#L169) reads startup environment variable `GGML_OP_OFFLOAD_MIN_BATCH`, defaulting to 32. For ordinary matrix multiplication its batch test uses output token columns. The [scheduler](https://github.com/ggml-org/llama.cpp/blob/091b6a7fc561b78da90a0ed2d524ec995458c657/ggml/src/ggml-backend.cpp#L1017) can run eligible operations using host-resident weights on a higher-priority CUDA backend when operation offload is enabled. The installed server enables it by default.

Thus microbatch 16 crosses a real CUDA eligibility boundary. This supports the observed CPU-heavy slowdown; an actual graph trace has not established every operation's placement or the complete cause. The CPU tiled IQ3 path has a separate floor of eight, so a CPU multiplication cutoff at 32 is not supported by the inspected source.

An environment value of 16 can restore eligibility during 16-token prefill but leaves single-token and four-token decode below the threshold. A value of one also permits eligible low-batch decode operations. This changes operation execution and temporary host-weight copies, not the declared 40 GPU layers. CUDA staging allocations, repeated transfers and game contention remain risks to measure. Four configured slots do not imply four token columns in every decode step.

A bounded header-only read of the installed GGUF, without CUDA initialization, found 65 blocks and 866 tensors. Assuming the default tail-layer placement with 40 GPU layers, the estimated CPU matrix footprint is 3.582 GiB excluding input-embedding row lookups; FFN and output matrices account for 2.568 GiB. These are aligned tensor-size estimates, not a graph trace or measured transfer volume. If that amount were copied per four-token decode step, 30 combined tokens/s would require roughly 19.3 to 26.9 GiB/s of host-to-device payload before other costs. The device reports a Gen5 x16 link, but effective bandwidth has not been measured. These numbers justify a diagnostic, not a throughput claim.

The prepared candidate is `.runs/qwen-gaming-threshold-20261021/gaming.override.yaml`, using `GGML_OP_OFFLOAD_MIN_BATCH=1` with the same three-bit model, 40 layers, three CPU quota/threads, b128/u16, four 40,960-token contexts and hard 12 GiB RAM/no swap. It supersedes an unexecuted env16 prefill-only diagnostic, preserved alongside it. Neither is the saved failed `docker-compose.gaming.yml` release candidate, and neither has been promoted.

The prepared `preflight.py` reuses the existing native benchmark for four requests of 512 prompt tokens and 32 output tokens, with a 90-second request deadline. It requires Qwen initially stopped and a fresh actual-gameplay baseline at least 60 FPS before loading. A separate screenshot worker supplies fresh gameplay frames during the probe. Resource checks cover startup and inference, missing GPU counters fail closed, and cleanup attempts unload even if child cleanup fails. Its diagnostic result requires the benchmark's original 30 combined tokens/s check, at least one fresh gameplay capture during the probe, no guard failure and successful unloading. It always records full-goal and half-hour acceptance as false. Static independent review passed; that is not a live performance result.

At preparation, Qwen remained stopped. Subsequent captures showed menus or obscured FPS despite the user's visibility confirmation. The final fresh check at 20:00:19 UTC refreshed the window inventory and again found the game/FPS obscured.
